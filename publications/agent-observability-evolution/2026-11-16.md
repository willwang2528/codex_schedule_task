## 1. DeFA: Dependency-Guided Failure Attribution for LLM Agents

**中文译名：** DeFA：面向大语言模型智能体的依赖引导失败归因

**方向：** Task D · 2026-11-16 · 轨迹处理与诊断反馈

**今日研究优先级：** #1

- **日期：** 2026-10-01
- **状态：** arXiv v1 预印本；未核实正式录用。
- **研究相关性：** 步骤规范化、协议关系恢复、分段摘要与依赖图生成诊断证据，归因反馈进一步用于持久技能更新。
- **入选理由：** 历史高价值补充；同时验证证据组织、归因和下游技能改进，直接连接两项研究重点。

### 一句话概述

DeFA 针对智能体错误与后续症状相隔较远的问题，通过重建步骤依赖和失败传播关系组织证据，并将归因反馈用于技能改进。

<details>
<summary>论文摘要翻译</summary>

大语言模型智能体执行中的错误及其可见后果可能相隔许多步骤，因此定位决定性错误需要同时理解步骤内容与步骤依赖。我们提出依赖引导的智能体失败归因框架 DeFA。它首先将协议关系与语义依赖结合成覆盖轨迹的事件依赖图，然后识别可能违反任务要求的事件，追踪其来源与后续影响，构建失败传播图；最后结合步骤证据及其在传播中的作用，识别决定性错误、责任智能体和错误类别。为支持长轨迹，DeFA 将执行划分为片段，将当前片段的详细内容与其他片段的摘要结合，使局部诊断获得全局上下文。在 Who&amp;When 和 Who&amp;When Pro 文本子集上，DeFA 在所有受评骨干模型上取得最高的责任智能体与精确步骤准确率，并在 Pro 上采用一致分类体系的方法中取得最高的失败类别准确率。图像与视频轨迹实验展示了其多模态归因适用性；消融支持分段、事件依赖图和失败传播图的贡献。将诊断反馈用于 Trace2Skill 的技能演化，相比原流程使下游任务准确率提高 6—15 个百分点，表明诊断也能支持智能体在后续任务上的改进。

</details>

<details>
<summary>现存问题</summary>

局部异常可能只是传播后的症状；长轨迹中的工具返回、委派关系和后续信息使用分散，直接判断难以区分错误来源与承接步骤。

</details>

<details>
<summary>已有方法的不足</summary>

全文判断、逐步检查和二分搜索未显式恢复完整依赖关系。本文与七种归因方法比较；语义边仍由模型解释，图结构本身不构成因果证明。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入为带角色和原始索引的步骤序列；压缩超长步骤后，模型生成协议匹配规则，确定性解释器配对请求与结果，再结合分段摘要恢复语义依赖。候选异常与传播图交给归因裁判，输出步骤、责任主体和类别。反事实判断属于模型推断，并非逐项环境干预。归因评估使用 Who&amp;When 的 184 条轨迹和 Pro 的 300 条文本轨迹；Pro 的责任主体指标只使用其中 89 条。下游以 100 个 SpreadsheetBench-Verified 任务演化技能、另 100 个测试，四种模型与初始技能组合均优于原 Trace2Skill；持久改变的是可复用技能。

</details>

<details>
<summary>未来展望</summary>

作者提出改善长轨迹关系识别，并扩展诊断反馈应用领域。编辑推断：可优先研究压缩与分段遗漏如何影响证据召回；现有实验不足以证明生产级海量轨迹处理能力。

</details>

## 2. Harness-S: Learning from Sibling Harnesses for Generalizable Agent Training

**中文译名：** Harness-S：通过同源运行框架学习可泛化的智能体策略

**方向：** Task D · 2026-11-16 · 诊断后自进化

**今日研究优先级：** #2

- **日期：** 2026-11-03
- **状态：** arXiv v1 预印本；官方仓库已有部分实现，未核实正式录用。
- **研究相关性：** 失败原因分组形成互补修复框架，以新执行轨迹训练持久策略参数，并回到原框架验证。
- **入选理由：** 将“辅助框架帮助当前执行”与“能力留在模型中”分开检验，具备原框架、重采样及固定混合对照。

### 一句话概述

Harness-S 针对不同运行框架只能修复部分失败的问题，通过失败引导的同源框架池生成救援轨迹，并把这些经验训练进共享策略。

<details>
<summary>论文摘要翻译</summary>

从共同基础演化出的运行框架具有局部性、互补性和非平稳性：不同变体修复不同失败，其效用也会随策略学习而变化。我们提出 Harness-S，不寻求普遍占优的框架，而是利用同源框架选择性救援基础执行系统的失败，并将所得能力迁移到一个在原始框架下仍有效的策略中。定向框架演化沿不同修复方向产生专门变体，形成可复用且在策略训练期间保持固定的框架池。互补救援训练仅在基础框架下的初始尝试全部失败时调用该池；同一策略在选定辅助框架下生成新轨迹，用这些轨迹替换失败组进行强化学习。自适应路由器利用框架行为画像和多个大语言模型投票选择 Top-k 变体；感知策略变化的画像重新校准会随学习刷新证据。在 AppWorld、SWE-Gym 和 DBBench 上，训练后的策略返回原始框架时显著优于仅训练策略的方法。行为分析与留出案例支持框架诱发行为向策略本身的迁移。在执行轨迹数量相同的条件下，将路由器复用于 Rank-1 推理还可带来额外收益。

</details>

<details>
<summary>现存问题</summary>

一种框架修复某类任务时可能损伤另一类任务；随着模型更新，过去有效的修复也可能不再适用。

</details>

<details>
<summary>已有方法的不足</summary>

只选单一最佳框架会丢失互补修复；固定混合与原框架重采样不能等价替代选择性救援。本文不属于递归改写优化算法：训练期间框架池、优化器和验证器固定。

</details>

<details>
<summary>当前方法为什么可行</summary>

失败任务的共同原因→定向框架编辑→验证覆盖驱动的父代选择与固定框架池；成对验证轨迹→行为画像→路由。基础框架的整组尝试失败后，同一当前策略从初始状态执行辅助框架，替换训练组并用 GRPO 更新参数。测试任务数为 AppWorld 262、SWE-Gym 160、DBBench 300；每任务三次执行，重复三个独立随机运行，Pass@3 与 Avg@3 分别报告。原框架测试支持能力保留。官方仓库首版侧重 AppWorld，默认关闭行为画像校准与模型投票，不能视为完整论文设置已复现。

</details>

<details>
<summary>未来展望</summary>

作者计划研究长期迁移、跨策略框架池复用及扩池的校准成本。编辑推断：应同时核算救援、画像刷新和训练成本；相同推理次数不代表端到端成本相同。

</details>

**原始来源：** [arXiv｜全文及官方仓库已核查](https://arxiv.org/abs/2611.04277)

## 3. Veritas: A Verifier Generation Harness for Agent Tasks

**中文译名：** Veritas：面向智能体任务的验证器生成运行框架

**方向：** Task D · 2026-11-16 · 验证反馈与回归评估

**今日研究优先级：** #3

- **日期：** 2026-11-09（arXiv 标注；北京时间 11-10）
- **状态：** arXiv v1 预印本；未核实正式录用。
- **研究相关性：** 声明可观测证据、生成可执行验证器，并利用验证反馈保留框架修改。
- **入选理由：** 把验证器可运行性、判断一致性与标签可信度分开评估，提供诊断后更新所需的验收机制。

### 一句话概述

Veritas 针对智能体自改进缺少可靠任务验证器的问题，通过明确可用证据、提供领域规则和约束编写原则来生成并检查验证器。

<details>
<summary>论文摘要翻译</summary>

自改进系统的有效性高度依赖验证器质量，因为验证器判断每轮改进的结果。然而，多数任务的验证器由人工编写，成本高，难以扩展到没有验证器的任务。我们提出自动生成验证器的运行框架 Veritas。不同于通用智能体框架，Veritas 增加了三种机制：说明验证器将观察什么的证据声明、任务中未明示的领域规则库，以及部分通过自改进循环完善的编写原则。我们在六个基准上评估：四个通过执行评分，其官方验证器先经过认证；另两个比较成对回答。在模型固定时，Veritas 生成的验证器在全部四个执行评分基准上，与官方判定的一致性均高于其他七种框架；在两个成对比较基准上处于或接近最佳水平。在另外三个模型家族中的两个上，它也比厂商自带框架具有更高的一致性。将这些机制加入其他框架，还改善了三个框架中十二个执行评分组合的九个。

</details>

<details>
<summary>现存问题</summary>

验证器可能检查实际不可见的信息、遗漏领域义务、拒绝等价正确解，或根本未交付可运行程序；错误验收会污染后续演化反馈。

</details>

<details>
<summary>已有方法的不足</summary>

通用编码框架不能保证理解验证时的信息边界，官方测试也不能无条件当作真值。本文的认证是针对受测任务和候选解，不能保证全部任务正确。

</details>

<details>
<summary>当前方法为什么可行</summary>

执行评分任务以任务说明和初始环境生成验证器；判断时再输入轨迹或最终状态，证据类型依基准而异。领域规则和编写原则约束判定，探测失败可触发一次修复。持久演化另有 32 轮、模型与研究者共同提案的过程，保留四项修改；不能称全自动演化。主表的 τ²-bench 与 SWE-bench 属于参与机制设计的 fit/validation 数据，终端基准更接近未见评估。四组执行评分分别覆盖 58/138/33/39 个任务、166/435/189/219 个候选；κ* 将缺失判定计错，不能当作任务成功率。并非全部机制都由演化循环发现。

</details>

<details>
<summary>未来展望</summary>

编辑推断：应在未参与设计的真实任务上检验验证器生成，并用独立人工与执行证据审计误拒绝；论文尚未证明接入任意 Agent 后会改善其长期任务成功率。

</details>

**原始来源：** [arXiv｜主记录与 v1 全文已核查](https://arxiv.org/abs/2611.13336)

## 4. EvoGroup: A Self-Evolving Harness for Group Agents in Shared Contexts

**中文译名：** EvoGroup：共享上下文中群组智能体的自演化运行框架

**方向：** Task D · 2026-11-16 · 轨迹筛选与诊断汇总

**今日研究优先级：** #4

- **日期：** 2026-11-02（arXiv 标注；北京时间 11-03）
- **状态：** arXiv v1 预印本；官方仓库目前仅有说明等占位文件。
- **研究相关性：** 置信度与结果联合筛选轨迹，按需读取局部证据，压缩诊断并跨轨迹汇总，驱动持久框架更新。
- **入选理由：** 直接研究“很多轨迹如何变成可用于修改的证据”；入选依据是诊断处理机制，实验范围限群组记忆任务。

### 一句话概述

EvoGroup 针对共享上下文中轨迹冗长且失败经验难以汇总的问题，通过置信度筛选、按需证据读取和分桶诊断来指导运行框架修改。

<details>
<summary>论文摘要翻译</summary>

随着 Claude Tag 等群组智能体兴起，智能体越来越多地成为长期团队协作中的数字工作者。它们运行于通过多用户交互持续积累的共享上下文。然而，现有智能体记忆系统主要面向个人用户，难以捕捉共享上下文中的群组关系和协作形成的知识；人工记忆策略也限制了对多样且变化的共享上下文的适应。我们提出 EvoGroup（EvoG），一种从最小六工具冷启动出发、通过共享上下文交互进行适应的群组智能体自演化框架。EvoG 利用置信度和任务结果选择信息丰富的轨迹，并在低置信度情况下引出对不确定性的自我反思。分析智能体通过自适应渐进披露检查所选轨迹，再通过分桶分析综合高层发现，指导演化智能体修改框架。实验中，EverMemBench 留出集的 pass@1 从 71.07% 提升到 89.58%，超过自演化记忆与人工设计框架，包括 Claude Code 的 85.83%。为评估泛化，我们冻结演化后的框架，在未见过的 GroupMemBench 上评估；使用 GPT-5.5 时，它展示了有效泛化，并超过记忆基线和人工框架。

</details>

<details>
<summary>现存问题</summary>

跨用户、会话和时间的信息形成长轨迹；成功也可能伴随不确定性，仅分析终局失败会遗漏脆弱行为。

</details>

<details>
<summary>已有方法的不足</summary>

全文一次性分析成本高；逐条诊断缺少跨案例汇总。分桶依据是查询语义类型，不应等同于发现真实根因簇。论文部分外部基线是公开分数的题量对齐投影，并非相同留出题目重跑。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入为查询、观察、动作与回答组成的轨迹；用置信度和外部正确性排除优先级较低的“自信且正确”组。分析器从结构视图按需展开片段，把详细诊断压缩为位置、原因和行动建议，再按查询类型汇总。输出指导表示、工具操作、边界检查及策略四类持久修改。EverMemBench 用 720 题演化、1,680 题留出评估，并开展冻结框架迁移；消融检查按需读取和分桶。已执行迭代不代表每次修改均通过严格回归门控，论文记录了任务回退。仓库尚不足以复现。

</details>

<details>
<summary>未来展望</summary>

作者计划扩展到更真实、长期、多样的多人协作。编辑推断：值得检验按故障机制而非查询类型聚合的收益，并加入更新前回归门控；跨领域和生产规模证据仍不足。

</details>

## 5. When Failures Propagate: Causal Failure Attribution in Agentic Retrieval-Augmented Generation

**中文译名：** 当失败发生传播：智能体式检索增强生成中的因果失败归因

**方向：** Task D · 2026-11-16 · 干预归因与重放评估

**今日研究优先级：** #5

- **日期：** 2026-10-29（正式论文集日期）
- **状态：** REALM 2026 workshop 正式论文；不是 EMNLP 主会论文。
- **研究相关性：** 保留注入位置与被修改证据，从污染前缀重新执行后缀，分别评估归因与恢复。
- **入选理由：** 历史高价值补充；给出可定位的干预标签，并揭示不同修复范围、位置先验和预算截断对归因结论的影响。

### 一句话概述

AgenticRAG-FP 针对多跳检索中故障传播后难以判断起点的问题，通过在已知位置注入错误并重新执行后续轨迹来评估归因方法。

<details>
<summary>论文摘要翻译</summary>

智能体式检索增强生成在多个跳次中交织检索、推理与答案生成。第一跳的检索错误可能直到第三跳才表现为错误答案，而后续检索也可能修复轨迹。本文提出用于智能体式 RAG 因果失败归因的干预基准 AgenticRAG-FP。基准在指定跳次注入经确认的故障，重新执行下游轨迹，并以已知干预位置评估诊断器。核心问题是：后缀变化后，事后轨迹能否仍识别注入跳次。在使用稠密检索、Claude Haiku 4.5 和三跳 MuSiQue 问题的结构故障实验中，基于覆盖率的诊断在第一跳为 0.91，在第二、第三跳均为 0.00，对应失败轨迹数为 43、36、21；但它在 96% 的失败中预测第一跳，表现为最早跳次规则。在第二、第三跳，LLM 裁判和冻结跳次修复只能定位 0.25—0.48 的失败。在规模更大的内容污染实验中，深度二的精确跳次准确率分别为：覆盖率方法 0.00、LLM 裁判 0.49、冻结跳次修复 0.59、后缀再生成 0.14，样本数为 51；裁判与冻结跳次修复没有显著差异，精确 McNemar 检验 p=0.33。

</details>

<details>
<summary>现存问题</summary>

后续检索会传播或吸收错误；最终答案正确性、定位注入位置和恢复能力是不同目标。

</details>

<details>
<summary>已有方法的不足</summary>

静态改写轨迹看不到智能体对故障的响应；最终答案覆盖率可能偏向最早跳次。修复后答对，也不等于找到了唯一真实根因。

</details>

<details>
