## 1. Forging More Tasks into Better Harnesses: Agentic Harness Evolution via Successive Scale Racing

**中文译名：** 将更多任务转化为更好的运行框架：通过逐级规模竞赛演化智能体运行框架

**方向：** Task D · 2026-10-25 · 证据选择与自进化

**今日研究优先级：** #1

- **日期：** 2026-10-20（arXiv 首发）
- **状态：** arXiv v1 预印本；正式录用未核实
- **研究相关性：** 任务轨迹→结构化经验→质量与覆盖度排序→持久 Harness 修改→执行竞赛。
- **入选理由：** 直接连接两条研究主线，并用固定候选数消融区分证据质量、覆盖度和规模的作用。

### 一句话概述

针对任务经验增多反而干扰智能体运行框架优化的问题，SSR 将轨迹整理为结构化经验，并通过代表性排序、多尺度候选生成和执行竞赛选择保留的修改。

<details>
<summary>论文摘要翻译</summary>

智能体运行框架演化将任务执行经验作为不断演变的证据，用于优化指令、工具和控制流程。直觉上，更多演化任务应当改善性能，但我们的初步研究发现一种反常失败模式：现有方法的性能随任务池扩大而下降。进一步分析表明，优化中的证据选择不佳导致这种退化，不同证据组合会产生显著不同的演化结果。为此，我们提出逐级规模竞赛（SSR），在每轮演化中自适应搜索最佳证据组合。SSR 根据相应任务的质量和覆盖度构建多样证据组合，并在较小计算预算下高效比较所得候选运行框架。在三个不同基准的全部六种配置中，SSR 取得最佳结果。尤其当任务池由 40 扩大到 200 时，SSR 的通过率由 64.3% 稳步升至 68.3%，而各基线均下降。此外，其竞赛机制在减少 60% 验证执行次数的同时找到了接近最优的候选。

</details>

<details>
<summary>现存问题</summary>

大量轨迹可能包含重复、冲突或难以行动的反馈；优化器实际需要的证据组合还会随当前 Harness 改变。

</details>

<details>
<summary>已有方法的不足</summary>

全量输入、固定子集或只按单条质量排序无法同时控制冗余与覆盖；作者也承认证据噪声不是规模退化的唯一可能原因。

</details>

<details>
<summary>当前方法为什么可行</summary>

每个训练任务产生一条轨迹；LLM 提炼摘要、修改建议及重要性/可行动性/置信度，嵌入相似度支持边际覆盖排序。不同长度的嵌套前缀生成候选；父代与候选在共享任务批次上竞赛，仅严格超过父代才保留代码或指令修改。选择分数混合验证任务与父代成功/失败的训练任务，并非纯验证集分数。SWE-Pro-V、DeepSWE、GAIA-2 的训练/验证/测试任务数分别为 80/20/100、50/13/50、80/20/100；主结果来自三次独立演化。60% 节省来自固定候选矩阵的选择回放，不代表整个系统节省同等成本；理论不保证跨轮单调提升。

</details>

<details>
<summary>未来展望</summary>

作者提出动态证据裁剪、细粒度轨迹信用分配及更广模型验证。编辑推断：可进一步按故障类型分层检查证据覆盖，检验罕见失败是否被排序机制遗漏；目前未证明生产规模有效。

</details>

**原始来源：** [arXiv 2610.28815 v1 原文](https://arxiv.org/abs/2610.28815)

## 2. What Did the Agent Actually Do? Evidence-Grounded Oversight for Long-Horizon Agents

**中文译名：** 智能体究竟做了什么？面向长程智能体的证据支撑监督

**方向：** Task D · 2026-10-25 · 轨迹证据组织

**今日研究优先级：** #2

- **日期：** 2026-10-05（arXiv 首发）
- **状态：** arXiv v1；官方仓库称 ICLR 2027 在审，非已录用
- **研究相关性：** 保留原始来源的证据单元→行为与作用域图→任务视图→监控判断和人工核验。
- **入选理由：** 历史高价值补充：把确定性证据整理与模型判断明确分开，同时评价证据定位和决策理解。

### 一句话概述

针对长程智能体的重要决策与支持证据分散的问题，EBG 将可追溯证据组织成行为图和任务视图，供监控模型识别需要用户核验的决策。

<details>
<summary>论文摘要翻译</summary>

随着智能体承担长程任务，用户从逐项决策转向监督自主执行，但活动数量庞大、支持证据分散，使人难以确定哪些决策需要核验。我们研究识别重要决策并定位证据的监控器，以帮助用户评估其影响。我们引入软件工程基准 AgentMonBench，其三个子集涵盖两个互补维度：需求与行为是否一致，以及是否识别出需要核验的重要自主决策。为支持这些判断，我们提出无需训练的证据支撑行为图（EBG），将关联原始来源的证据归入行为，并将行为关系组织为图。EBG 提供面向任务的图视图，帮助监控器结合上下文理解行为。八个模型的实验显示，相比直接访问原始上下文，EBG 在多数设置下改善决策识别和证据定位。进一步实验表明，证据定位收益跨输入规模和超参数设置保持存在，实际应用也展示了其支持人工监督的实用价值。

</details>

<details>
<summary>现存问题</summary>

最终任务成功不能说明是否悄悄改变了评估指标、遗漏需求或作出需要确认的决定；相关证据可能分布在代码、消息和工具结果中。

</details>

<details>
<summary>已有方法的不足</summary>

直接阅读长上下文与局部代码检索难以组织跨位置行为关系；但找到证据仍不等于理解决策后果，论文的失败分析明确区分两者。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入有仓库与轨迹两类。轨迹按助手段落及配对的工具调用/结果拆成证据单元，保留来源与位置；确定性程序形成需求—行动—响应行为，按任务作用域保序组织，再交给 LLM 判断。仓库采用条件—操作—结果及一跳图扩展。三个子集各 100 个样本，只有 FeedbackTrace 是交互轨迹；不能写成 300 条 Agent 轨迹。八模型比较使用相同实例；FeedbackTrace 的 EHR 仅要求命中至少一个参考证据 ID。五个 Codex 应用案例展示核验用途，未验证持续自进化或大规模吞吐。

</details>

<details>
<summary>未来展望</summary>

作者建议改善内容级覆盖，并固定证据内容研究组织方式与推理过程的影响。编辑推断：其来源标识可供后续诊断和回归复用，但将监督发现自动转成可靠修复仍缺实验。

</details>

**原始来源：** [arXiv 2610.06406 v1 原文](https://arxiv.org/abs/2610.06406)

## 3. Self-Evolving Agents through Privileged Retrospective Distillation

**中文译名：** 通过特权回顾式蒸馏实现智能体自进化

**方向：** Task D · 2026-10-25 · 反馈驱动参数更新

**今日研究优先级：** #3

- **日期：** 2026-10-20（arXiv 首发）
- **状态：** arXiv v1 预印本；正式录用未核实
- **研究相关性：** 成功/失败轨迹→先例、教训、逐轮反思与后见信息→词元监督→持久模型参数更新。
- **入选理由：** 明确检验经验能否内化进模型，并将核心自蒸馏与需要更强外部反馈的上下文策略演化区分。

### 一句话概述

针对自然收集的智能体轨迹缺少标准答案和训练奖励的问题，RSD 利用跨任务经验与事后反馈重新评估已执行动作，再将监督分布蒸馏进模型参数。

<details>
<summary>论文摘要翻译</summary>

自进化智能体旨在从自身经验中改进，而非部署后保持固定，但自然收集的轨迹往往缺少标准答案或验证器提供的奖励。我们提出回顾式自蒸馏（RSD），利用特权回顾上下文，将这些经验转为稠密监督的多轮框架。对于每条在策略轨迹，同一个底层模型同时充当学生和教师：教师结合跨任务先例与教训，以及完整轨迹中的轮次级反思和未来后见信息，重新评分学生实际执行的动作。所得教师分布通过在策略自蒸馏回传给策略。随着轮次推进，经验库增长、回顾上下文刷新，使模型、数据和监督共同演化。我们还引入前沿模型引导的上下文策略演化，让更强模型在约束范围内修改特权上下文的构建方式。在 ALFWorld、ScienceWorld 和 SearchQA 上使用 Qwen3-8B 与 Qwen3-14B 时，RSD 相对基础模型的性能提升最高为 59.7%；相比固定上下文策略，前沿模型引导的演化进一步带来最高 44.7% 的相对提升。结果表明，核心策略更新无需标准答案轨迹或验证器奖励，也能将自然累积的经验转为持久模型能力。

</details>

<details>
<summary>现存问题</summary>

失败轨迹包含动作后果，却缺少可直接监督当时动作的正确目标；只保存经验不保证下次执行能力改变。

</details>

<details>
<summary>已有方法的不足</summary>

成功轨迹筛选会丢失失败反馈；奖励优化依赖验证信号；推理时反思或经验注入也不等于参数学习。各基线监督权限和交互预算不同，不能视为等成本比较。

</details>

<details>
<summary>当前方法为什么可行</summary>

以轨迹、交互轮和动作词元为处理单位：筛选并检索先例、按任务类型总结教训，结合当前轨迹的事后反思与后续观察，固定教师分布后用前向 KL 更新全部参数。实验运行十轮、每轮采样 200 个训练实例；主结果平均三个种子，学生通常不带特权上下文推理。ALFWorld 使用 seen/unseen 验证划分，ScienceWorld 为 449 个开发变体，SearchQA 为测试集。扩展版以环境指标选择和接纳上下文策略，拒绝时只回退策略而不回退参数；教师冻结也使用选择指标。因此不能称整个系统无验证器，或把所有结果称为隔离测试集收益。

</details>

<details>
<summary>未来展望</summary>

作者观察到 SearchQA 的经验内化有限，教师持续变化还可能造成后期退化。编辑推断：应增加独立保留集、错误反思污染和参数回滚对照，区分稳定学习与选择指标适配；生产持续学习证据不足。

</details>

**原始来源：** [arXiv 2610.27495 v1 原文](https://arxiv.org/abs/2610.27495)

## 4. VeriEvolve: Evaluator-First Evolution for Tool-Using Agents

**中文译名：** VeriEvolve：面向工具使用智能体的评估器优先演化

**方向：** Task D · 2026-10-25 · 评估器与工作流演化

**今日研究优先级：** #4

- **日期：** 2026-10-21（arXiv 首发）
- **状态：** arXiv v1；作者记录称 EMNLP 2026 REALM 非归档研讨会接收；官方名录未核实
- **研究相关性：** 执行状态差异→反事实挑战状态→回归约束下的评估器修订→持久工作流候选。
- **入选理由：** 把验证标准本身纳入反馈闭环，并清楚暴露外部校准、状态可观测性和执行能力的限制。

### 一句话概述

针对有状态工具任务缺少可靠优化信号的问题，VeriEvolve 先生成可执行评估器，在冻结评估器下演化工作流，再利用执行状态差异修订评估器。

<details>
<summary>论文摘要翻译</summary>

自改进智能体面临的核心障碍之一，是现实有状态任务缺乏可靠的适应度信号。我们提出评估器优先的演化框架 VeriEvolve，在优化智能体之前先构建缺失的评估层。它根据每项任务指令合成有指令依据的挑战状态，以及检查这些状态的可执行评估器。每轮工作流演化期间，评估器保持冻结并提供适应度信号；轮次之间，框架将强弱执行结果的终态转换为成对反事实测试用例，以修订评估器。在 MCPMark Filesystem 全部 30 项任务上，它构建了 30 个评估器及 141 个挑战状态，在生成测试集上达到 141/141 的一致性，在执行智能体产生的留出状态上达到 113/122。评估器引导的演化使 GLM-5.2 经外部验证的成功数从 6/30 增至 18/30，Claude 从 27/30 增至 30/30；修订消除了弱执行器暴露的全部三个假阳性。PostgreSQL、Playwright、Notion 和 GitHub 的跨环境研究进一步揭示了可观测性、状态表示与搜索/执行能力的互补限制。这些结果表明，当任务成功可观测且外部验证器可用于校准时，可以合成可执行评估器来引导搜索。

</details>

<details>
<summary>现存问题</summary>

最终文字声称完成，并不能证明文件内容、目录结构、保存要求或副作用符合指令；内部评估器也可能漏掉约束。

</details>

<details>
<summary>已有方法的不足</summary>

人工验证成本高，语义裁判不一定检查真实状态；本研究仍没有等预算搜索基线，无法将全部提升单独归因于评估器指导。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入指令和只读初始状态，生成挑战状态及确定性检查程序；检查级反馈和执行轨迹用于追加工作流节点的提示/行为备选，保留旧备选供重组。强弱终态差异被聚类为缺失、内容或结构问题，构造正负状态对，经累计回归后保存评估器新版本。30 个文件系统任务各条件仅跑一次；122 个不同留出状态来自每轮内部择优结果，并非独立随机样本。外部验证器决定研究准入、假阳性触发与正参考状态；修好三个评估缺口后，仅一个对应任务被弱执行器解决，不能把评估器修复等同于 Agent 修复或跨任务泛化。

</details>

<details>
<summary>未来展望</summary>

作者把去除外部验证器依赖列为关键下一步，并建议强化搜索、执行及专用修订模型。编辑推断：应先验证独立触发机制及等预算对照，再声称无人监督的自演化；现有实验不足以支持该结论。

</details>

**原始来源：** [arXiv 2610.29005 v1 原文](https://arxiv.org/abs/2610.29005)

## 5. AgentLoupe: Kernel-Resident Semantic Causal Labels for AI Agent Observability

**中文译名：** AgentLoupe：用于 AI 智能体可观测性的内核驻留语义因果标签

**方向：** Task D · 2026-10-25 · 事件采集与关联重建

**今日研究优先级：** #5

- **日期：** 2026-10-16 首发；v2：2026-10-19
- **状态：** arXiv v2；作者记录称 PACMI 2026 研讨会接收，ACM 正式记录访问失败
- **研究相关性：** TLS/系统事件→内核链标签传播→协议重建与按链聚合→风险分析证据。
- **入选理由：** 历史高价值补充：以资源身份连接延迟执行和跨进程事件，贡献超出日志展示；案例证据有限，列第五。

### 一句话概述

针对智能体延迟执行和跨进程活动难以追溯的问题，AgentLoupe 将语义链标签随内核资源传播，并重建按链组织的审计证据。

<details>
<summary>论文摘要翻译</summary>

AI 智能体通过工具调用将用户意图转化为系统动作。将这些动作准确归因到最初的 LLM 交互，对安全审计至关重要，但 AgentSight 等现有方法无法处理延迟执行和跨进程谱系行为。我们提出对应用透明、基于 eBPF 的可观测工具 AgentLoupe，核心思想是将因果身份嵌入内核资源。它使用 eBPF 捕获 TLS 明文以解释 LLM 交互，并为每次交互赋予内核驻留的语义标签；标签保存在 eBPF 映射中，跨进程和线程传播，并关联文件、套接字等内核资源。当持久资源把上下文传递给原进程谱系以外的独立进程时，该设计保留延迟的因果关联。实验显示平均观测开销低于 8%，案例研究确认它能将跨谱系持久攻击追溯到最初的 LLM 交互。

</details>

<details>
<summary>现存问题</summary>

框架内工具日志看不到独立守护进程之后执行的动作；仅靠进程树或短时间窗口也会丢失持久文件传递的联系。

</details>

<details>
<summary>已有方法的不足</summary>

应用层埋点缺少系统副作用，传统系统来源追踪缺少具体 LLM 交互语义。论文对这些差异给出机制与案例说明，尚无广泛攻击基准上的关联准确率比较。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入为 TLS 明文片段及进程、inode、套接字事件；内核按明确资源交接传播 chain_id，独立提示建立新链并保留跨链关系。用户态解压、重组 HTTP/SSE、恢复顺序，按链聚合至 SQLite，过滤已知噪声后供 LLM 风险分析。三个工作负载各重复五次比较时间开销；两个案例分别记录 165 与 126 条原始日志，不能外推为高吞吐或大规模验证。资源依赖关联不等于语义根因证明，分析器置信度也不是实测准确率；本文未执行诊断后的自进化。

</details>
