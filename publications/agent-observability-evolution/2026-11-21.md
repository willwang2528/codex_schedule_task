## 1. Agentic Harness Engineering Beta: Requirement-Centered Evolution of Agent Harnesses

**中文译名：** 智能体运行框架工程 Beta：以需求为中心的运行框架演化

**方向：** Task D · 2026-11-21 · 诊断后自进化

**今日研究优先级：** #1

- **日期：** 2026-11-18（arXiv 首次提交；北京时间 11-19）
- **状态：** arXiv v1 预印本；未核实正式录用
- **研究相关性：** 会话证据→经核验需求→跨会话归并→提示词、工具和中间件代码的持久修改→审查与留出评测。
- **入选理由：** 更新：此前已报道 AHE；本篇独立后续论文将选择依据改为已验证需求与审查，并引入多轮用户模拟和团队修改，提供完整闭环证据。

### 一句话概述

针对运行框架演化容易形成任务特定补丁的问题，该研究把用户交互与运行日志转化为经核验需求，再通过团队修改和需求审查保留框架变更。

<details>
<summary>论文摘要翻译</summary>

现实中的运行框架工程由显式和隐式用户需求驱动，需求指导开发与验证；但现有演化方法常忽视隐式需求和交互需要，由单个演化智能体修改框架，再按基准分数选择变更，因而容易产生狭窄补丁并陷入基准特定的局部最优。本文提出以需求为中心的 AHE-Beta，将现实工程实践引入框架演化：首先，模拟用户在多轮使用中以问题单提出需求；其次，团队式修改将需求实现为可泛化变更，而非任务特定补丁；最后，仅当变更解决经验证的需求并通过审查时才合并。在留出任务上，AHE-Beta 将 pass@1 从 21.9% 提升至 33.3%，比基础框架少用 40.8% 的 token，且 pass@1 高于 Claude Code、Meta-Harness 和 AHE。在盲测人类 A/B 比较的 48 个有效配对中，用户有 31 次偏好 AHE-Beta，并在全部五个维度给出更高评分，与模拟用户的偏好方向一致。作者据此认为，AHE-Beta 达成了使框架演化贴近现实用户需求的目标。无需进一步演化，收益可迁移至 GLM-5.3 和 DeepSeek-V4.1-Flash，相对基础框架的 pass@1 分别增加 15.8 和 5.3 个百分点。作者总结，以需求为中心的框架演化是一种更具一般性的智能体能力改进方法。

</details>

<details>
<summary>现存问题</summary>

单一终局得分难以说明用户为何不满意；日志中的任务偶然细节又容易被写成专用补丁。关键缺口是把交互失败变成可追溯、可复核且可实现的通用需求。

</details>

<details>
<summary>已有方法的不足</summary>

论文对照的自动演化方法主要依赖基准得分筛选修改，难覆盖隐式交互需求。前作 AHE 已有分层轨迹证据与修改预测，本篇新增的是需求驱动的组织和合并机制；不能把全部可观测性设计都算作首次提出。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入为带版本定位的会话、运行日志、问题单及评分；分诊先核实问题并去除任务答案等特定信息，架构角色归并共同机制，形成引用原始证据的需求和设计方案；开发角色修改提示词、工具或中间件，代码与需求审查通过后合并持久提交，模型权重不变。证据不足时记录补充观测的需求，而非强行归因。论文在 38 个留出任务上评测，主配置重复三次；摘要中的 token 节省只计执行阶段，不含演化成本。人类证据单位是 48 个有效 A/B 配对，并非 48 名独立用户。整体闭环已运行，但不能据此识别每个组件的独立因果贡献。

</details>

<details>
<summary>未来展望</summary>

作者讨论的边界包括模拟用户的代表性及基础模型能力瓶颈。编辑推断：可将经核验需求作为跨轨迹诊断的中间对象，再增加需求级回归与撤销记录；现有证据不足以保证开放生产环境中的长期收益。

</details>

**原始来源：** [已核验的一手论文](https://arxiv.org/abs/2611.24924)

## 2. TIDE: Trajectory-based Diagnostic Evaluation of Test-Time Improvement in LLM Agents

**中文译名：** TIDE：基于轨迹诊断评估大语言模型智能体的测试时改进

**方向：** Task D · 2026-11-21 · 轨迹诊断

**今日研究优先级：** #2

- **日期：** 2026-10（EMNLP 正式发表）；初稿 2026-02-02
- **状态：** EMNLP 2026 主会论文，官方论文集与最终 PDF 已核验
- **研究相关性：** 状态—动作序列→完成进度曲线、循环片段与记忆干预差值→过程诊断及回归评估。
- **入选理由：** 历史高价值补充：把完成效率、行为循环和历史上下文效用分开测量，弥补仅按终局成功判断的盲区；未在本任务历史中报道。

### 一句话概述

针对终局指标难以解释交互中的进展停滞问题，TIDE 将执行轨迹转化为任务完成动态、循环行为和工作记忆效用的诊断指标。

<details>
<summary>论文摘要翻译</summary>

自主大语言模型智能体的近期进展表明，它们能够通过与环境迭代交互来改善表现，本文将这一范式定义为测试时改进。可是，这种改进为何成功或失败，其机制仍不清楚；现有评估指标无法捕捉任务优化效率、错误动作后的行为适应，以及工作记忆的具体效用。为弥补这些缺口，本文提出测试时改进诊断评估框架 TIDE：它轻量、不依赖特定智能体或环境，将测试时改进分解为三个全面且相互关联的维度。该框架测量任务完成的整体时间动态，并识别表现是否受到递归循环行为或累积记忆负担的限制。通过广泛实验，TIDE 强调，改进智能体表现需要显式优化智能体与环境之间的交互动态。

</details>

<details>
<summary>现存问题</summary>

相同终局成功率可以对应不同的解决速度、重复操作和上下文负担，失败也可能来自重复访问相同状态，而非缺少知识。

</details>

<details>
<summary>已有方法的不足</summary>

终局成功率不能定位过程瓶颈，单看长度也不能区分必要探索与无效循环。TIDE 的循环判定依赖环境的状态等价规则；重复不自动等于错误，指标关联也不等于根因证明。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入是逐步状态、动作和成功判定。AUV 对截至每步已完成任务的比例曲线积分并按步数预算归一化；LR 将连续重复的非嵌套状态—动作循环定位为片段，以重复动作数除以总动作数；MI 比较完整历史与仅保留任务及当前观测时的 AUV。前两项整理轨迹，后一项必须额外做受控运行，不能仅从既有日志推断。论文主要比较 17 个模型在五类环境中的表现，并补充桌面与移动端轨迹分析。它输出诊断量和可检查片段，没有训练或保留新的 Agent 策略。

</details>

<details>
<summary>未来展望</summary>

作者指出仍需处理更复杂环境与多智能体情形。编辑推断：这些指标适合作为诊断后修改的回归观测项，但必须同时检查最终任务目标；尚无证据证明仅优化这些指标就能带来持续自进化。

</details>

**原始来源：** [已核验的一手论文](https://aclanthology.org/2026.emnlp-main.639/)

## 3. How Much Should an Agent Remember? Deployment Lessons from Self-Distilled Memory for LLM Agents

**中文译名：** 智能体应该记住多少？大语言模型智能体自蒸馏记忆的部署经验

**方向：** Task D · 2026-11-21 · 轨迹处理与经验更新

**今日研究优先级：** #3

- **日期：** 2026-11-19（arXiv 首次提交；北京时间 11-20）
- **状态：** arXiv v1；作者注明 IAAI 2027 Oral 录用，会议名单未独立核验
- **研究相关性：** 成功/失败轨迹→经验提取、聚类去重及来源保留→持久化操作指南→后续任务注入与评估。
- **入选理由：** 部署研究的价值在于公开归并、来源丢失、错误经验和评估混淆；不将其包装为全新记忆算法或全自动安全演化。

### 一句话概述

针对智能体反复出现的程序性错误，该研究从执行轨迹提取经验并归并为带来源和支持计数的持久指南，再按模型需求注入后续任务。

<details>
<summary>论文摘要翻译</summary>

执行长程任务的大语言模型智能体会反复出现程序性失败，例如错误处理 API 分页、匹配错误实体，或在用户未要求回答时作答。作者构建了一条让智能体从自身历史学习的流程：先从每段执行轨迹挖掘一至三条简短经验，再归并为较少的指南，每条记录合并了多少经验。推理时，智能体接收全部指南或选出的子集。流程作为开源 altk-evolve 库发布，并部署于 IBM 的 CUGA 智能体和 watsonx Orchestrate 平台。本文报告构建、测量和产品化过程中的经验，主要使用 AppWorld，覆盖基线任务完成率为 40%—92% 的模型。核心发现是：合适的记忆数量取决于模型，而非记忆本身。强模型随指南增加继续获益；DeepSeek-V3.2 使用完整的 191 条指南后，任务完成率和场景完成率分别增加 9.5 和 16.1 个百分点。弱模型使用同样的完整指南集，收益反而小于使用精选子集：gpt-oss-120b 的任务完成率从 39.9% 起步，使用全部 199 条指南达到 51.2%，使用约 29 条精选指南则达到 55.4%，后者为两次运行均值。围绕这些结果，作者报告了产生反效果的高支持度指南、归并中静默丢失的来源信息、导致全部任务失败却留下貌似正常日志的被吞掉 API 错误，以及几乎造成与既有方法误导性比较的基线混淆，并将这些问题整理为记忆部署建议。

</details>

<details>
<summary>现存问题</summary>

重复经验会挤满检索名额，归并又可能丢失来源；出现次数多的指南也可能是错的。记忆是否写入成功、到底改变了什么，必须能独立检查。

</details>

<details>
<summary>已有方法的不足</summary>

简单增加或压缩指南不能统一适配各模型；支持计数只表示复现频率，不表示正确性。论文明确其贡献是部署经验，未声称提出全新算法；高支持错误指南的修正仍包含人工判断。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入来自 train/dev 的成功和失败轨迹，以官方任务判定区分证据极性；提取经验后聚类并合并行为等价项，保留来源、支持数及未覆盖条目，要求输出支持数之和等于原始经验数。持久指南通过全量或高支持核心加语义检索注入，模型权重不变。DeepSeek 的 147 条轨迹产生 290 条经验、191 条指南。主要评估为 AppWorld test_normal 的 168 个任务：TGC 是通过全部检查的任务比例，SGC 是所有任务变体均通过的场景比例。作者直接在 test_normal 比较配置，多数为单次运行；最佳配置存在测试集选择偏差，不能视为独立泛化验证。

</details>

<details>
<summary>未来展望</summary>

作者建议先校验来源、实际读写、运行噪声、固定框架及 token 成本。编辑推断：把指南支持度与正确性检查分开，并用独立留出任务决定保留或撤销，才能把这类经验更新接到可信的诊断后演化闭环；论文尚未验证这一完整自动门控机制。

</details>

**原始来源：** [已核验的一手论文](https://arxiv.org/abs/2611.26361)

## 4. CompAct-Bench: A Benchmark for Working-Context Compaction in Long-Horizon Agent Tasks

**中文译名：** CompAct-Bench：长程智能体任务的工作上下文压缩基准

**方向：** Task D · 2026-11-21 · 压缩与续跑评估

**今日研究优先级：** #4

- **日期：** 2026-11-19（arXiv v1 首次提交）
- **状态：** arXiv v1 基准论文；未核实正式录用
- **研究相关性：** 历史步骤→定长压缩上下文→还原中间环境并续跑→区分信息遗漏与状态歪曲。
- **入选理由：** 用续跑后的真实任务判定评价压缩，直接连接轨迹压缩、失败诊断和回归；避免只按摘要文字质量判断。

### 一句话概述

针对历史压缩可能破坏后续执行的问题，CompAct-Bench 在任务中途压缩工作上下文并恢复对应环境，以续跑行为检查信息保留与状态表达。

<details>
<summary>论文摘要翻译</summary>

长程智能体在交互历史逼近模型上下文上限时越来越依赖上下文压缩。多数系统将这一过程交给语言模型，把累积历史改写为较短的工作上下文，但现有模型的压缩能力仍缺乏充分理解。为此，本文提出 CompAct-Bench：一个包含 200 个任务的过程级基准，通过 BrowseComp、SWE-bench 和内部 CompanyBench 套件覆盖信息检索、软件工程与工作区自动化。对每个实例，待评估模型在中间边界压缩历史，固定执行器从对应环境状态出发，在匹配的动作预算下继续执行。作者评估了十二个前沿语言模型作为压缩器。尽管保留的每个任务都在压缩前的三次筛选运行中完成，压缩后的平均准确率仍降至 56.7%，最佳模型也仅达到 68.5%。失败分析揭示两条路径：信息遗漏导致重复工作和预算耗尽；状态歪曲则可能把暂定证据变成结论，引发过早终止。通过把工作上下文压缩变成可测量、影响执行的模型能力，CompAct-Bench 为构建跨越上下文窗口边界仍然可靠的长程智能体奠定基础。

</details>

<details>
<summary>现存问题</summary>

压缩会丢失已尝试的动作、未完成事项或证据的不确定性；摘要看似连贯，执行器仍可能重新探索或错误结束任务。

</details>

<details>
<summary>已有方法的不足</summary>

依赖摘要相似度或静态问答的评价无法直接检验环境交互后果。该基准提供过程干预，但其任务经过稳定成功筛选，不能把测得的损失推广为所有真实任务的平均压缩风险。

</details>

<details>
<summary>当前方法为什么可行</summary>

从三次均成功且足够长的任务中保留一条参考轨迹；200 个任务分别分配一个中间边界，而非每项生成三个实例。历史压到目标 10% 的可压缩历史字符保留比例（不含固定系统/任务头），经长度校准后恢复边界环境，由固定执行器在剩余动作预算内续跑三次，以 Avg@3 平均任务判定计分，不是 pass@3。任务构成为 79 个检索、96 个代码和 25 个内部工作区任务。模型化失败标注结合证据引用与部分人工检查，可支持遗漏/歪曲分析，但不构成人工因果金标准。它评估压缩器，没有实现诊断后持久策略更新。

</details>

<details>
<summary>未来展望</summary>

作者将该基准定位为可靠长程上下文管理的基础。编辑推断：可据失败定位修改压缩规则，再在相同边界做配对回归；内部工作区数据及自动标注限制仍需补足，尚不能宣称整套基准均可公开复现。

</details>

**原始来源：** [已核验的一手论文](https://arxiv.org/abs/2611.25673)

## 5. Validation-Driven Deployment of LLM Inference Platforms for Agentic Workloads

**中文译名：** 面向智能体工作负载的大语言模型推理平台验证驱动部署

**方向：** Task D · 2026-11-21 · 轨迹重建与负载回放

**今日研究优先级：** #5

- **日期：** 2026-11-19（arXiv v1 首次提交）
- **状态：** arXiv v1 系统研究；公开数据集页面已核验，未核实正式录用
- **研究相关性：** 完整模型请求→OTel span 与依赖图→保留时序的工作流回放→服务容量、覆盖与版本回归。
- **入选理由：** 提供实质的轨迹规范化、依赖重建及回放验证；补齐链路中的评估基础设施，明确区别服务负载与任务行为。

### 一句话概述

针对智能体推理服务各验证阶段的数据难以衔接的问题，该研究将完整请求轨迹规范化并重建依赖关系，用工作流回放连接测试、容量规划和回归分析。

<details>
<summary>论文摘要翻译</summary>

企业正把智能体工作负载从封闭 API 迁移到自建开放权重模型部署，因此，从小规模测试、容量规划、预生产到生产的全生命周期验证愈发重要。通常部署评估依赖临时拼装的工具，而这些工具的准确性很少被检查。本文提出面向智能体大语言模型服务的端到端评估流程，并用实证支持连接各阶段的设计选择。实验表明，回放捕获的轨迹能够再现原始智能体会话的逐会话负载：在第 95 百分位，回放的输入 token 数保持在记录值的 1.18 倍以内，而实时重跑可达 4.98 倍，因此少量记录会话可以产生可重复的逐会话 token 负载。对 vLLM 的代码覆盖分析进一步表明，在所测配置中，实时、回放和合成负载互为补充，各自触达了其他负载的已测运行未覆盖的 Python 服务路径。在使用 llm-d 部署四个大型混合专家模型的案例中，相比公开轨迹，目标模型在捕获负载上的最优并发约为一半，相应吞吐量约为 60%。作者开源了相关工具并发布轨迹数据集。

</details>

<details>
<summary>现存问题</summary>

只有请求长度直方图不足以重放真实会话；重新运行 Agent 又会因路径变化导致负载漂移，从而混淆服务版本回归与工作流随机性。

</details>

<details>
<summary>已有方法的不足</summary>

传统负载生成器常丢失请求内容及调用依赖，Agent 任务评测又常把服务端当成固定条件。论文的服务层回放不执行真实外部工具，而是复用记录工具结果，因而不能替代任务正确性与环境副作用的回归测试。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入为请求消息、工具参数、时间和会话标识；转换为 OTel GenAI span，再用消息匹配及时间回退规则构建依赖 DAG，并按父调用完成与记录间隔调度回放。依赖是重建结果，不能直接当作失败因果关系。公开语料报告 10,056 个会话、241,674 次调用；主要保真评估仅使用 80 个会话，二者不是同一规模。代码覆盖结论限于所测配置的 Python 路径。生产案例的约 220 万请求是聚合统计，并非同等规模完整 Agent 轨迹；论文没有证明 Agent 自身在回放后得到改进。

</details>

<details>
<summary>未来展望</summary>

作者将更完整的生产轨迹捕获与大规模合成工作负载验证列为后续方向。编辑推断：可在诊断后修改的验收中并列设置任务行为和服务负载两道回归检查；目前证据不足以把负载保真等同于语义执行保真。

</details>
