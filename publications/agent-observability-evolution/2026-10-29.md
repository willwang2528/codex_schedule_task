## 1. Trial by Trace: Benchmarking AI Agent Harnesses for Reliability and Failure Attribution

**中文译名：** 以轨迹为据：面向可靠性与失败归因的 AI Agent 运行框架基准

**方向：** Task D · 2026-10-29 · 轨迹数据处理与诊断

**今日研究优先级：** #1

- **日期：** 2026-10-23
- **状态：** arXiv v1 预印本；未核实正式录用
- **研究相关性：** 原生运行事件→保留来源的 TraceIR→有界多源证据包→分层评估与运行级归因；未执行持续自进化。
- **入选理由：** 首次报道；将事件关联、证据选择、任务成功和运行框架可靠性拆开核验，直接对应本研究链的数据处理与诊断接口。

### 一句话概述

针对任务完成情况难以揭示运行框架缺陷的问题，该研究将原生执行事件和环境证据整理为可追溯证据包，并结合分层评估与机制链分析定位失败。

<details>
<summary>论文摘要翻译</summary>

大语言模型 Agent 日益用于解决现实问题，其有效性既取决于底层模型，也取决于支持其运行的框架。然而，现有基准大多关注模型能力和 Agent 的整体表现，对运行框架的评估关注有限。为弥补这一缺口，我们提出 TraceTrial-Bench，将框架可靠性组织为上下文、执行、治理、生命周期、可观测性、工具和验证七个组成部分。我们构建了 95 个专家级、面向机制的任务，以可执行或基于状态的真值，在保留各框架原生行为的同时支持语义等价比较。我们设计轨迹追踪模块来捕获 Agent 执行轨迹，并提出分别评估 Agent 表现与框架可靠性的双层评估体系。此外，多源证据获取模块从 Agent 上下文、框架和执行环境中提供证据供大语言模型评估使用；失败归因模块通过显式机制链支持运行级归因。对四种框架、九种模型和 95 个任务的 3,420 次运行进行评估后，框架宏平均得分介于 59.8% 与 72.0% 之间，31.1% 的运行虽然完成任务，却至少未通过一项框架标准。TraceTrial-Bench 为框架比较、失败诊断及框架设计与模型行为交互研究提供了可审计、可复现的基础。

</details>

<details>
<summary>现存问题</summary>

任务通过不代表上下文管理、工具关联或验证机制正常；仅看最终答案，也难以区分模型决策、框架行为和外部环境造成的失败。

</details>

<details>
<summary>已有方法的不足</summary>

整体任务分数会混合模型与框架因素；不同运行时的原生记录又不能直接对齐。作者提出语义等价任务，但并未消除不同接口、裁判预算与任务修订带来的全部比较差异。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入是原生事件、工作区差异、模拟器真值和外部探针。事件先转为带 run_id、序号、时间戳和 raw_event 的 TraceIR；工具调用与返回依原生标识关联，歧义项保留未关联状态。确定性选择器按事件类型、字段和关键词生成有界证据包，保留匹配数、返回数及截断标记，完整档案仍可回查；之后才由裁判评分和机制链支持归因，证据整理不等于因果推断。
论文的 3,420 是四框架×九模型×95 任务的所选运行数，不是每个配置的重复试验；1,065/3,420 次任务成功仍有框架标准未通过。缺失必需证据也可能计零，不能一律解释为确认缺陷。论文未量化选择器召回率、裁判一致性或候选机制链接精度，亦未验证诊断后的自动修复闭环。

</details>

<details>
<summary>未来展望</summary>

作者提出以轨迹支持修复，并用受控干预、重复执行和固定条件检验机制。编辑推断：可借鉴其证据包接口，但应先测证据选择召回率和归因一致性，再将诊断接入自动更新；现有实验不足以证明因果归因或持续改进。

</details>

## 2. Failing Agents Leave Traces: Telemetry Signatures for Multi-Tier Agent Evaluation

**中文译名：** 失败的 Agent 会留下痕迹：用于多层 Agent 评估的遥测特征

**方向：** Task D · 2026-10-29 · 轨迹聚合与失败筛查

**今日研究优先级：** #2

- **日期：** 2026-10-29（论文 PDF 标注的会议出版日期）
- **状态：** REALM 2026 工作坊论文集；非 EMNLP 主会研究论文
- **研究相关性：** span／步骤遥测→每条轨迹的计数、产物大小和熵→阈值告警或分类分数；用于筛查，不是根因证明。
- **入选理由：** 首次报道；提供低推理成本的轨迹筛查机制，并公开与裁判并联时的漏报、误报及标签口径，适合研究大规模证据分流。

### 一句话概述

针对逐条轨迹审查成本高的问题，该研究将工具调用、令牌消耗和产物大小聚合为行为特征，通过阈值与分类器筛查需要进一步评估的运行。

<details>
<summary>论文摘要翻译</summary>

当前 Agent 评估依赖逐条轨迹的大语言模型裁判推理或人工审查，成本高到无法覆盖每条轨迹，生产系统因而只抽查其中一部分。我们发现，失败的 Agent 会在标准可观测性遥测中留下可检测的行为特征：相对于结果付出了不成比例的努力。我们形式化了四种行为失败特征，并在覆盖五个 Agent 领域的 4,671 条轨迹上验证：补偿性投入——各领域主要信号对应的投入增加 17%—159%，五个领域均成立，p&lt;0.006，且在所有测试领域都是主导特征；输出膨胀——SWE-rebench 中补丁增大 38%，其方向与可靠性随领域而变；无聚焦编排——五个领域中的四个令牌熵增加 5.98%—12.3%；相关性解耦——三个领域中，成功与失败轨迹的投入信号相关性出现结构变化，p&lt;0.001。仅对这些信号进行简单阈值检查，无需裁判、标签或模型调用，已能捕获 52.9%—61.5% 的失败。在三个人工标注基准中，裁判在其中两个可直接比较的基准上漏掉 6.5%—18.1% 的已确认失败；训练后的遥测分类器 AUROC 为 0.821，能找回各裁判漏报的 61.5%—75.4%。将裁判与分类器结合后，相对于八个受测裁判中最弱的 GPT-4o-mini，漏报率从 18.1% 降至 4.4%，约缩小为原来的四分之一；更强裁判本来漏报较少，相应降幅也较小。

</details>

<details>
<summary>现存问题</summary>

抽样审查遗漏大量运行，单看答案的裁判也可能漏掉过程异常；但投入增多既可能反映困难任务，也可能反映无效循环，不能直接视为失败原因。

</details>

<details>
<summary>已有方法的不足</summary>

全文裁判和人工审查成本高；仅靠遥测则会漏掉低投入的错误。标签也不统一：τ-bench 子集按失败 API span 标注，AppWorld 按 Agent 自报完成状态标注，均不等同独立任务成功真值。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入是每条轨迹的 span／步骤、令牌、工具调用和输出产物；聚合为计数、总量与熵，再用无标签分位阈值或监督分类器输出风险标记。相关性解耦属于成功／失败轨迹群体的统计比较，不能当作单条轨迹的根因定位。
五领域共 4,671 条轨迹，不是一次在线流处理规模。AgentRewardBench 的 1,301 条中有 946 条人工确认失败、355 条成功；裁判与分类器取 OR 后检出 904/946 个失败，但将 183/355 个成功误报，误报率 51.5%，精确率从 0.926 降到 0.831。Counsel 的 131 个确认错误中有 20 个没有投入升高。结果支持补充筛查，不能据此证明无漏检、跨域通用分类器或线上持续自进化。

</details>

<details>
<summary>未来展望</summary>

作者提出多层监控及后续严重度加权评估，但未执行并验证 Agent 更新闭环。编辑推断：可将遥测用于审查排序，并保留低风险样本的随机审计；各域需单独校准阈值与误报成本，不能按投入低直接丢弃轨迹。

</details>

## 3. Harness Evolution Hits a Ceiling: When Weight Training Should Begin

**中文译名：** 运行框架进化遇到瓶颈：何时应开始训练模型权重

**方向：** Task D · 2026-10-29 · 诊断后自进化

**今日研究优先级：** #3

- **日期：** 2026-10-08
- **状态：** arXiv v1 预印本；未核实正式录用
- **研究相关性：** 失败组成与代表轨迹→框架编辑及验证保留→进化轨迹训练 LoRA／权重→留出任务交叉评估。
- **入选理由：** 历史高价值补充；把诊断信号、持续更新对象和留出验证连接起来，并通过框架×权重交叉实验区分改动依赖。

### 一句话概述

针对失败后难以判断应修改运行框架还是训练模型的问题，该研究依据轨迹中的失败组成进行框架进化与轨迹训练，并交叉评估不同框架和模型权重。

<details>
<summary>论文摘要翻译</summary>

改进长时程大语言模型 Agent，可以进化冻结模型周围的运行框架，也可以训练模型权重。我们沿同一研究路线考察两者：先让自进化框架强化系统，再交叉组合初始与进化后的框架、基础与训练后的权重，辨别哪些收益被模型保留，哪些仍依赖运行时。我们表明，可以从 Agent 的失败组成中判断应采用哪种手段。按最先触发的信号标注失败轨迹，可区分过程失败——调用受阻、循环、步数预算耗尽——与内容失败，即交付的计划质量差。框架进化修复前者，它促成的行为可以训练进权重，而内容失败是权重训练的目标。在具有留出划分和可验证评分的规划基准 DeepPlanning 上，大语言模型提出框架编辑、裁判进行验证的自进化循环，将 Qwen3.5-4B 的留出得分从 0.16 提至 0.30，将 Qwen3.5-9B 从 0.32 提至 0.44；收益出现在假设对应的位置：4B 的留出交付率从 55% 增至 90%，循环减少，而内容失败留待权重处理。消融将收益定位到赋予能力的组件，而非强制约束；循环自身的证据包解释了它为何停在该处。随后，在进化框架轨迹上训练的 LoRA 适配器将收益内化：在原始框架下，两种规模的留出得分都增加 0.13；4B 上它与框架叠加，使留出得分增至两倍以上；9B 上仅适配器便达到完整进化路线的水平，内容失败从约四分之一轨迹降至二十分之一。用答案打乱轨迹训练的安慰剂适配器表现低于基础模型，说明收益来自轨迹内容；在更大轨迹集上全量微调又增加 0.04。同一循环迁移至 WebArena-Lite，在 117 个未见任务上增加 0.09；这里收益来自模型看见的信息，即两页历史而非一页，在这些轨迹上训练适配器没有额外收益。由此形成两次应用的先诊断后干预规则：先依据失败组成，为过程失败进化框架、为内容失败训练权重；再依据接受的编辑改变了什么，将改变模型输出的收益训练进去，而对改变模型可见信息的收益保留框架。得分为相对新测参考配置的四次 rollout 均值；除特别注明外，比较均在同一夜完成，覆盖六个模型家族的八个模型及两个基准。

</details>

<details>
<summary>现存问题</summary>

总分上升无法说明问题来自运行约束、循环、计划内容，还是可见信息不足；也无法说明优化后是否仍需保留原来的运行组件。

</details>

<details>
<summary>已有方法的不足</summary>

通用反思缺少可执行的更新选择依据，单看优化后的总分不能区分框架与权重贡献。本研究也未与等计算预算的推理时搜索系统比较，诊断分类不是独立标注的因果真值。

</details>

<details>
<summary>当前方法为什么可行</summary>

轨迹按首个触发信号归入证据不支持、框架摩擦、循环／预算耗尽或低质量已交付计划；评分、健康指标和失败案例组成提案证据包。提案模型编辑提示、工具与中间件，经开发集回归检查和新测参考配置比较后保留；进化轨迹再用于持续的 LoRA／权重更新。
DeepPlanning 用 48 个开发任务决策、72 个留出任务评估，交叉测试初始／进化框架与基础／训练权重；核心比较取四次 rollout 均值，部分消融有另行注明的较少重复或跨夜条件。答案打乱对照仅在相应模型设置成立。作者发现提案证据包未聚合评分器的具体失败组成，因此瓶颈也可能来自证据缺失；不能把该结果推成框架优化的普遍上限。计划转 JSON 的评分转换也存在经审计的偏差。

</details>

<details>
<summary>未来展望</summary>

作者讨论向提案器暴露评分器失败组成；已有初步尝试未得到可分辨收益。编辑推断：应先检验诊断证据是否足够，再决定训练权重；仍需预算匹配对照及其他环境验证，不能把该经验规则当作普遍因果规律。

</details>

## 4. Travel Back To Move Forward: Retrospective Exploration and Evolving for Long Horizon Agents

**中文译名：** 回到过去以继续前进：长时程 Agent 的回溯探索与进化

**方向：** Task D · 2026-10-29 · 失败反馈与策略更新

**今日研究优先级：** #4

- **日期：** 2026-10-09
- **状态：** arXiv v1 预印本；未核实正式录用
- **研究相关性：** 执行分支与状态恢复记录→状态锚定续行比较、反思进展奖励→持久策略权重更新；反思记忆限于当前任务。
- **入选理由：** 历史高价值补充；不仅增加重试，还训练执行与反思策略，提供状态恢复、轨迹归组和消融证据，补足持续策略更新环节。

### 一句话概述

针对早期错误使长时程任务陷入死路的问题，ReTRAIL 将环境回退与失败分支反思结合，并利用状态锚定的续行比较和后续探索进展训练共享策略。

<details>
<summary>论文摘要翻译</summary>

大语言模型 Agent 越来越多地在长时程环境中运行，早期错误可能引发级联失败，并使 Agent 陷入死路轨迹。因此，Agent 必须能够主动从这些状态中恢复，并把探索经验转化为后续决策的指导。我们提出 ReTRAIL，使 Agent 能将环境回退到较早状态，同时保留有效进展，并携带从已放弃探索中学到的知识。环境状态向后移动，而 Agent 的知识继续向前推进。ReTRAIL 用两种互补信号训练共享策略：状态锚定 GRPO 比较重访状态后的不同续行以改进执行，分支推进奖励则根据后续探索的进展指导反思。在 MineSweeper、Sokoban、ALFWorld 和 ScienceWorld 四个交互基准上的实验表明，仅加入回退原语收益有限，甚至可能损害表现。相比之下，ReTRAIL 使 Agent 能从无效状态回退，并用放弃分支中得到的认识指导后续探索。这些结果说明，对长时程任务求解，将环境回退与进行中任务内的经验复用结合具有价值。代码地址为 https://github.com/whi497/ReTRAIL。

</details>

<details>
<summary>现存问题</summary>

放弃错误分支时，简单清空历史会丢失失败经验；保留全部历史则混杂已失效的环境状态。反思文本是否有用，也缺少与后续行动进展相连的训练信号。

</details>

<details>
<summary>已有方法的不足</summary>

只开放回退工具不保证 Agent 会正确选择恢复时机或利用经验；普通最终奖励难区分执行和反思的贡献。研究依赖可恢复环境，不能直接替代真实外部操作的补偿与验证。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入为交互轨迹、状态快照／重放记录及被放弃分支。在线上下文分离保留前缀和废弃后缀，回退前生成反思，恢复环境后携带反思继续；完整训练档案保留原上下文和分支联系。按任务、环境状态和保留前缀对齐续行，以段回报训练执行 token，以新旧分支进展差训练反思 token，共享策略权重持续更新；任务内记忆不等于跨任务持久经验库。
四基准测试集分别为 128、128、140、1,661 个实例，报告三种子均值；ALFWorld 使用 valid_seen。T@1 与 T@3 的恢复机会不同，不能将差值单独归因于反思；每次试验总限 60 次模型调用，反思也计入。训练附录中基线与 ReTRAIL 的调用上限不同，不能将名义尝试数匹配等同实际 token／计算预算匹配。原始后缀替代反思及移除进展奖励的消融支持组件作用，但不是独立因果诊断真值。

</details>

<details>
<summary>未来展望</summary>

作者提出近似恢复、补偿动作、状态检查以及跨回退边界的信用分配。编辑推断：迁移 GUI／Web 前，应独立验证恢复后的环境状态，并计入恢复成本；现有可重置基准不足以证明对不可逆现实操作的适用性。

</details>

## 5. Knsight: Self-Evolving Agentic System for Production Cloud Root Cause Analysis

**中文译名：** Knsight：面向生产云环境根因分析的自进化 Agent 系统

**方向：** Task D · 2026-10-29 · 方法迁移与技能更新

**今日研究优先级：** #5

- **日期：** 2026-10（论文集出版月；会议日期 10-24—10-29）
- **状态：** EMNLP 2026 Industry Track 正式论文；非主会研究轨道
- **研究相关性：** 方法迁移：外部云遥测→图像证据画布→诊断与审查→自身事故重放通过的持久技能库；不是 Agent 轨迹大规模处理研究。
- **入选理由：** 首次报道；有生产部署、反馈转技能及保留／淘汰机制，补充可执行验证环节；云遥测输入与 Agent 经验更新分开解释。

### 一句话概述

针对云故障诊断中文本化遥测丢失时序与拓扑结构的问题，Knsight 将遥测组织成图像画布进行迭代审查，并把经重放验证的诊断经验保存为可复用技能。

<details>
<summary>论文摘要翻译</summary>

云事故响应越来越依赖大语言模型 Agent，将异构遥测和自然语言告警转化为面向运维人员的诊断。然而，在生产根因分析流程中，Agent 通常将这些结构化信号序列化为文本，丢失对诊断至关重要的时间和拓扑结构。我们提出已部署于工业环境的根因分析 Agent Knsight，将运行遥测转为图表图像画布，并使用冻结的多模态大语言模型直接基于视觉证据推理。Knsight 引入视觉递归思维 V-RoT，即迭代的诊断、审查和细化循环，Reviewer 模块检查每张画布并决定细化、放大或停止。为适应反复出现的生产故障，Knsight 进一步将 Reviewer 反馈转为推理时使用的共享技能库，并通过别名替换进行抽象。离线 OpenRCA 基准上，Knsight 的聚合 Correct 指标比最强纯文本基线高 7.0 个百分点，超时次数从 117 降至 11。在线 90 天部署覆盖 1,284 起生产事故，首位诊断接受率从 38.9% 升至 71.4%，确认用时和解决用时分别减少 59% 和 32%。

</details>

<details>
<summary>现存问题</summary>

外部日志、指标和调用链转为长文本后，时间对齐和拓扑关系容易丢失；每次事故重新诊断，又难以稳定复用已验证的诊断步骤。

</details>

<details>
<summary>已有方法的不足</summary>

文本式 ReAct 不直接保留图表结构，未经验证的反思也可能固化错误。文中生产比较不是盲法随机试验，运维人员确认仍可能带来选择和标注偏差。

</details>

<details>
<summary>当前方法为什么可行</summary>

外部云指标、日志、调用链与拓扑先转换为固定坐标、带哈希的 PNG／JSON 画布；Supervisor 与 Reviewer 在限定候选和时间窗口内选择 STOP、REFINE、ZOOM，输出时间、组件、原因。运维确认后的诊断动作序列经过别名化，并在来源事故上重放验证后入库；检索技能指导后续事故，滚动统计支持淘汰。持续改变的是外部程序性技能，模型权重冻结。
OpenRCA 的 335 个任务使用空技能库，因此相对基线的 Correct 改进不能作为自进化收益。CloudRCA 技能消融报告 Correct 为 60.0% 对 55.9%，与运维首位接受率 71.4% 是不同指标；确认用时覆盖全部 1,284 起事故，解决用时仅统计接受诊断的事故。自身事故重放不是独立泛化验证；正文不足以确认严格按时间隔离的技能评估。生产遥测吞吐量也不能换算为已处理 Agent 轨迹数。

</details>

<details>
<summary>未来展望</summary>

作者将学习型控制策略列为后续方向，并讨论漂移和技能维护。编辑推断：可迁移画布证据与验证后入库机制，但应追加时间隔离的前瞻回归；确定性画布重放也不自动保证模型决策复现，需固定模型与调用条件。

</details>
