## 1. When the Critic Falls Behind: Co-Evolving Rubrics and Harnesses for Continual Agent Self-Improvement

**中文译名：** 当评判者落后时：协同演化评价准则与运行框架，实现 Agent 持续自我改进

**方向：** Task D · 2026-10-31 · 诊断后自进化

**今日研究优先级：** #1

- **日期：** 2026-10-27
- **状态：** arXiv v1 预印本；正式录用未核实
- **研究相关性：** 失败轨迹聚合 → 动态行为准则 → 持久化 Harness 修改 → 独立验证集准入。
- **入选理由：** 把诊断标准的过时问题纳入更新闭环；包含准则生命周期、保守排序、验证门槛及留出评估，直接连接两条研究主线。

### 一句话概述

针对 Agent 运行框架迭代后旧评价准则难以反映新弱点的问题，RuHarness 从执行轨迹持续更新行为准则，并以这些准则指导经过验证的运行框架修改。

<details>
<summary>论文摘要翻译</summary>

自主 Agent 越来越依赖围绕大语言模型管理交互、记忆、工具与执行的运行框架。近期工作已开始利用执行经验演化这些框架，但指导演化的监督信号往往相对静态，难以追踪不同轮次中不断变化的行为弱点，也可能限制对未见任务的泛化。为解决这一问题，我们提出 RuHarness，一种用于 Agent 持续自我改进的评价准则与运行框架协同演化框架。RuHarness 不断从执行轨迹中发现并重新评估行为准则，优先处理最相关且尚未解决的弱点，在保持任务目标不变的同时指导有针对性的运行框架更新。跨多种 Agent 任务与骨干模型的广泛实验表明，RuHarness 优于强运行框架演化基线，尤其是在未见的留出任务上。进一步分析表明，自适应准则优先级能够追踪变化中的弱点，并支持跨演化轮次更持续的改进与稳定泛化。

</details>

<details>
<summary>现存问题</summary>

框架修改会改变失败分布：旧准则可能继续强调已解决的问题，也可能漏掉新出现的弱点；需要把跨任务失败转成可复核、可更新的诊断依据。

</details>

<details>
<summary>已有方法的不足</summary>

直接依赖任务成败或固定 rubric，难以保持诊断指导的时效性。论文比较 ACE、EvoSkill、Self-Harness、Meta-Harness、AHE，并消融固定准则与优先级模块；并非所有既有方法都完全不使用诊断。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入为演化任务的执行轨迹；逐条失败运行形成结构化报告，再聚合跨任务模式为准则。裁判在不知道最终结果的条件下给出满足、违反或不适用，随后结合成败统计进行准入、休眠/重启及后验下分位排序。高优先级准则指导修改工具/技能、指令、行动、观测处理、上下文或终止逻辑；候选通过一致性检查后，在独立验证集上超过当前框架的分数门槛才保留，模型权重固定。论文在 EvoAgentBench 五域、两种骨干模型上执行闭环，演化/验证/测试集分离；三随机种子验证仅覆盖两个代表性设置。行为准则与失败相关不等于证明因果根因。

</details>

<details>
<summary>未来展望</summary>

作者明确提出扩展到更多 Agent 架构、更长周期和开放环境；目前仅使用一个底层框架及固定演化时长。编辑推断：可进一步检验准则变化能否预测真实修复收益，并评估反复使用验证集的过拟合；现有证据不足以证明长期生产环境自进化。

</details>

## 2. Trajectory-Aware Benchmark Subset Selection for Cost-Efficient Software Engineering Agent Regression Testing

**中文译名：** 面向软件工程 Agent 低成本回归测试的轨迹感知基准子集选择

**方向：** Task D · 2026-10-31 · 轨迹数据处理

**今日研究优先级：** #2

- **日期：** 2026-09-21；所读 v2 更新于 2026-09-28
- **状态：** arXiv v2 预印本；正式录用未核实
- **研究相关性：** 异构日志 → 步骤规范化与泄漏清理 → 轨迹表示 → 代表性任务子集 → 更新后回归评估。
- **入选理由：** 历史高价值补充：把轨迹处理直接连接到回归测试选择，并通过时间切分、消融与随机抽样尾部风险比较验证其决策价值。

### 一句话概述

针对编码 Agent 更新后全量回归评估开销高的问题，该方法将历史执行轨迹规范化、去噪并编码为向量，再按历史成败分层选择具有代表性的测试任务。

<details>
<summary>论文摘要翻译</summary>

自主软件工程 Agent 能自动完成修复问题和实现新功能等复杂编码任务。评估这类 Agent 需要在大量真实软件任务上运行大型基准，而每次 Agent 更新后可能都要重新运行完整基准来发现退化和改进，单轮消耗数亿个大语言模型 token，使评估成为开发瓶颈。一种办法是只评估基准实例的子集，但随机抽样或依据历史成败进行分层随机抽样等简单方法，可能产生高方差和缺乏代表性的子集。为此，我们转向 Agent 轨迹，即其解决实例时逐步采取的行动和获得的观测。既有工作分析轨迹以刻画行为和失败模式，但据我们所知，没有工作用轨迹选择应评估哪些实例。我们提出依据轨迹嵌入进行确定性选择，替代随机抽样：先按近期完整运行中的测试结果分组，保持历史通过/失败比例，再在轨迹嵌入空间中选择子集。我们在同配置重跑、模型及配置变化、Agent 框架变化三种回归场景下，系统评估随机抽样、嵌入选择、聚类选择以及先缩小候选池再抽样等共 76 种配置。最好的轨迹感知方法选择各结果组中最靠近质心的实例，在所评方法中取得最低估计误差；这里的误差是子集与完整基准的问题解决率之差。例如，使用 5% 或 10% 的测试实例时，相比最强基线的典型抽样，平均估计误差降低 3–11%，最坏误差降低 4–11%；相比其第 95 百分位抽样，最坏误差降低 38–46%。最坏误差指任一单轮中子集与完整基准解决率的最大差距。结果显示，10% 的轨迹感知子集使估计误差中位数低于 5%，同时将 token 成本降低约 90%。

</details>

<details>
<summary>现存问题</summary>

更新后的 Agent 需要频繁回归，但小规模随机子集可能漏掉行为类型，使总体解决率估计失真；平均误差还会掩盖一次抽样的尾部风险。

</details>

<details>
<summary>已有方法的不足</summary>

历史结果分层约束难度构成，却仍随机挑选组内实例；纯行为聚类也不能替代结果分层。正文的 TOSEM 和占位 DOI/会议信息不足以确认正式发表，本次只认定为 arXiv 预印本。

</details>

<details>
<summary>当前方法为什么可行</summary>

异构日志先还原为步骤级行动与观测，再遮蔽标识符、仓库信息及显式结果词，并清除格式噪声；清理需按数据集人工校准。每步嵌入后，组合均值、标准差及首/中/末步骤为轨迹向量；按历史通过次数分层，组内取靠近质心的任务用于后续运行。研究数据分别为 25,279 条 SWE-Rebench 轨迹、3,000 条多模型轨迹及 3,500 条跨框架轨迹，不是单次处理量；后两者来自同一 500 实例池的不同运行。评估用历史运行选子集、后续运行测解决率误差；重采样分布有重叠，作者承认显著性可能偏乐观。官方仓库 README 已核对，但未运行复现。

</details>

<details>
<summary>未来展望</summary>

作者提出自动化泄漏清理、改进时序表示、扩展 Web/工具任务及增量更新子集。编辑推断：应用到诊断后自进化时，应另设罕见失败与安全回归集合；估计总体解决率准确，不代表一定能发现低频新故障。

</details>

## 3. Does Failure Feedback Direct Agent Self-Modification?

**中文译名：** 失败反馈会引导 Agent 的自我修改吗？

**方向：** Task D · 2026-10-31 · 诊断反馈验证

**今日研究优先级：** #3

- **日期：** 2026-10-10
- **状态：** arXiv v1 预印本；正式录用未核实
- **研究相关性：** 失败证据 → 指令/辅助代码修改 → 目标修复、同类迁移与留出净收益的分离评估。
- **入选理由：** 历史高价值补充：提供逐次修改的随机化测量，直接检验诊断是否指导修复，避免把候选筛选后的涨分当成诊断能力。

### 一句话概述

针对自修改后的分数变化无法说明失败反馈是否引导修复的问题，该研究通过随机选择反馈目标并控制修改条件，分别测量定向修复、同类失败迁移和留出任务净变化。

<details>
<summary>论文摘要翻译</summary>

自我改进的 Agent 使用失败反馈修改代码或指令，但筛选后的收益并不能证明针对目标的修复或泛化。我们通过比较随机选定的目标失败与父代其他失败的修复情况，测量修改的定向性。在公开 Darwin Gödel Machine 日志中符合条件的 145 次修改上，我们没有检测到目标特异性的优势。使用小型开放模型进行的受控指令修改实验表明，相关反馈能够改善目标修复。在一项预先制定分析计划的第二研究中，相比匹配的同类别反馈，目标反馈使 Qwen3-4B 的修复率提高 20 个百分点；Phi-4-mini 提高 7 个百分点，但不显著。目标修复并不可靠地意味着留出集改进。留出收益集中于具有可识别、可修复失败机制的设置，包括人为植入的错误和自然出现的工具接口失败。编辑定位和回归筛选的收益因设置而异，而八步修改循环与 GEPA 最终达到相近的平均留出准确率。评估应分别报告目标修复、对相关失败的迁移以及留出集的净变化。

</details>

<details>
<summary>现存问题</summary>

一个修改可以修好展示给编辑器的例子，同时破坏更多原本正确的任务；保留优胜候选也会提高最终成绩，因此总体涨分无法单独证明反馈有效或诊断正确。

</details>

<details>
<summary>已有方法的不足</summary>

只报告演化最终成绩、诊断文本合理性或筛选后候选，混合了编辑质量、选择效应与任务迁移。定向性检验本身也有边界：共同原因被统一修复时，定向性可以为零，不能据此宣布反馈无用。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入为父子版本、随机目标、修改提案及逐任务结果；中间统计分别比较目标与其他失败、同类与异类失败，并以“修复数减破坏数”除以评估任务数计算净变化。受控实验持久修改 playbook 或工具辅助库，第二研究分离诊断、验证与测试集；循环仅保留验证分数不降的候选，并作预算匹配的 GEPA 比较。指令设置的 D/V/T 为 180/180/240 题，工具设置为 120/120/180 题。DGM 的 145 次是满足纳入条件的修改，不是全部尝试；小模型、人工故障、单次子代评分及部分 oracle 定位限制外推。

</details>

<details>
<summary>未来展望</summary>

作者建议每次修改同时记录目标修复、其他失败修复和正确答案损失，并报告筛选前后质量。编辑推断：可将这些量作为诊断→修改闭环的独立验收指标；是否适用于大规模生产轨迹和更强模型，证据仍不足。

</details>

## 4. Compaction Laundering: Provenance Destruction in Context-Compacting Coding Agents

**中文译名：** 压缩洗白：上下文压缩型编码 Agent 中的来源信息破坏

**方向：** Task D · 2026-10-31 · 轨迹压缩与来源

**今日研究优先级：** #4

- **日期：** 2026-10-21
- **状态：** arXiv v1 预印本；正式录用未核实
- **研究相关性：** 带角色消息 → 历史序列化/摘要 → 来源核验 → 故障机制定位；贡献是数据处理与防护验证，不是自动自进化。
- **入选理由：** 历史高价值补充：定位摘要前的来源丢失机制，并区分内容残留、身份洗白和实际执行，为诊断证据保真提供具体反例。

### 一句话概述

针对编码 Agent 压缩历史时把外部内容误记成用户指令的问题，该研究追踪消息序列化中的来源丢失，并通过保留角色类型和核对真实用户消息来约束摘要归因。

<details>
<summary>论文摘要翻译</summary>

长时间运行的编码 Agent 必须压缩上下文：总结对话、丢弃原始内容，并把摘要作为记忆继续使用。我们表明，在流行的开源编码 Agent 中，这一步构成可被利用的信任边界。某些运行框架把带类型的对话摊平成单个纯文本字符串，用诸如 [User]: 的文本标签标记消息，在摘要模型运行之前就已在代码中破坏了消息来源信息。能控制 Agent 所读内容的攻击者可以伪造用户轮次，使其在压缩后作为真实指令保留。在五种摊平式框架 pi、opencode、Cline、Aider、OpenHands 中，伪造授权以 87–100% 的比例洗白进入 Agent 记忆，测试上下文最长约 908,000 token；在保留角色类型的 Codex、Gemini CLI、Qwen Code、Continue 四种框架中，相同攻击的成功率为 0%。我们进一步追踪了攻击的实际执行后果：被洗白的持续授权使真实使用工具的 Agent 在沙箱中执行攻击者控制的 curl | sh，并在真实 pi TUI 的端到端测试中达到约 50%，对应的配对干净对照为 0%。同一通道还会让 Agent 的计划避开攻击者指定的禁止访问文件，使代码审查可能忽略植入的后门。由于来源信息已被框架代码确定性地破坏，提示词层面的防御无法恢复它；我们评估的一项代码级来源检查捕获了 77% 的洗白，同时把 2% 的合法摘要内容降级。该缺陷也可在序列化器中直接修复：摊平前转义角色标签；保留角色类型的框架则通过始终保留消息角色避免这一缺陷。

</details>

<details>
<summary>现存问题</summary>

压缩可能保留一句话却丢失其说话者及可信来源，随后把外部文档中的陈述升级成用户授权；因此文本保真不等于诊断证据保真。

</details>

<details>
<summary>已有方法的不足</summary>

摘要提示词中的防注入要求无法补回序列化时已丢失的结构。论文所列分类器性能来自其他研究，并非同条件复测；角色类型对照的零成功率也不意味着框架抵御所有提示注入。

</details>

<details>
<summary>当前方法为什么可行</summary>

分析单位是带角色消息、摘要中归于用户的声明及后续执行。论文在固定提交的序列化器/摘要提示词上构造对照，并将摘要声明与保留的真实用户轮次做来源对比，无法支持的声明被降为未归因内容而非直接删除。E10 每框架 15 次测试，主要是组件级搭建；真实产品端到端证据仅为 pi：攻击链 3/6，对照压缩后 0/5，另一次干净运行在压缩前已执行，不能混作攻击成功。防护的误降分母为干净摘要的 324 条声明，且尚未测试自适应攻击。论文所链代码仓库本次不可读；以上是论文报告，并非本地复现。

</details>

<details>
<summary>未来展望</summary>

作者提出在摘要结构中携带来源、避免把摘要重新标作用户，并进行独立裁判及跨模型验证。编辑推断：轨迹清洗、聚合和检索应保留原始角色与证据索引；自动修复这些框架并验证长期收益的闭环尚未建立。

</details>

## 5. How Do Coding-Agent Harnesses Self-Evolve? An Empirical Study of Retrospective Adaptation

**中文译名：** 编码 Agent 的运行框架如何自我演化？一项回顾式适应的实证研究

**方向：** Task D · 2026-10-31 · 持久修改的回归验证

**今日研究优先级：** #5

- **日期：** 2026-10-26
- **状态：** arXiv v1 预印本；正式录用未核实
- **研究相关性：** 会话轨迹 → 回顾提案编码 → 持久配置修改 → 后续任务中的加载、使用及行为复发验证。
- **入选理由：** 逐项迁移修改并区分“问题出现、经验覆盖、修改被读取、行为改变”，补足自进化收益判断中常被跳过的机制证据。

### 一句话概述

针对回顾生成的持久修改是否会影响后续编码任务尚不明确的问题，该研究分析会话中的修改提案，并在同仓库后续任务上分别验证修改的可用性和目标行为是否再次出现。

<details>
<summary>论文摘要翻译</summary>

编码 Agent 可以根据先前任务的经验调整运行它们的软件、配置和指令，即运行框架，但这些调整是否改善后续任务中的行为仍不清楚。我们研究 /retro，这一技能要求 Agent 回顾已完成的会话并提出运行框架修改，考察它提出什么修改，以及实施后的修改是否减少后续任务中的重复工作。我们在 30 个 SWE-bench Verified 问题上运行 Claude Code，对 /retro 产生的 125 项提案进行定性编码，实施其中 24 项，并在同一仓库的后续问题上，以有无每项修改的全新会话评估 12 项运行框架修改。大多数提案引用了会话中的事件，但 43 项 lint 相关提案中有 18 项无论实际发生什么都会推荐某种实践。在未修改会话遇到目标问题的七项评估中，两项修改消除了目标动作，一项减少了出现次数，四项没有减少；部分修改还给无关问题增加了工作。运行框架自我演化需要的不只是生成和实施修改，还需要确定修改是否有益于后续任务，并修订或移除无益的修改。

</details>

<details>
<summary>现存问题</summary>

从一次会话中保留的失败清单可能不覆盖下一次遇到的错误；文件进入上下文或被读取，也不保证 Agent 按其内容行动。

</details>

<details>
<summary>已有方法的不足</summary>

将多项修改一起带入重试，或只看更新后的总成功率，难以辨认哪项经验在什么条件下生效。本文补充逐项跨问题迁移，研究过程有人工选择和评价，并不是全自动闭环。

</details>

<details>
<summary>当前方法为什么可行</summary>

输入为完整会话轨迹及编号提案，先编码经验触发关系与修改机制，再筛选可持久化、可定义复发标准的提案，形成指令文件、失败清单或配置。最终评估 11 项实施所得适应加 1 项作者编写的对照，共 13 个迁移事件；每事件原则上原版/修改版各 5 个全新容器会话。只有至少 3/5 原版会话遇到目标问题才计为信息充分事件。论文分开检查覆盖、加载、查阅及复发；未发现任务成功率一致改善，减少某个动作也不一定缩短运行。提案初始编码来自两个 LLM，再由作者裁决，不能称为人类标注者间一致性。

</details>

<details>
<summary>未来展望</summary>

作者计划覆盖其他 Agent、代码导航和编码规范，拆分捆绑修改，并在未针对目标问题挑选的后续任务上评估。编辑推断：可把“适用条件与覆盖范围”随经验保存，并设置持续回归淘汰机制；现有小样本不足以估计任意生产任务的受益比例。

</details>
