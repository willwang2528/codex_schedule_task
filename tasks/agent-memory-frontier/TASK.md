Create my daily Agent Memory research briefing using a two-stage research-and-filtering workflow.

Stage 1 — Build a broad candidate pool. Search across the Agent Memory core area and adjacent areas that could materially affect Agent Memory research, including long-horizon agents, continual/lifelong agents, context management, experience/trajectory reuse, retrieval/RAG for agents, skill/procedural memory, reflection/self-improvement, world models/belief state, personalization, and GUI/Web agent memory. Use this source priority: (1) formally published high-quality papers and official conference proceedings; (2) strong recent arXiv preprints and OpenReview submissions/reviews; (3) official research blogs and technical reports from leading labs/companies; (4) official GitHub repositories, benchmark, dataset, and evaluation releases; (5) researcher/community signals only as discovery leads, which must then be verified against primary sources. Prefer first-party/primary sources and do not treat reposts or social-media summaries as evidence.

Stage 2 — Independently validate and filter the candidate pool before sending anything. Do not simply pick the five newest items. For every serious candidate, assess: research significance, novelty beyond repackaging existing memory pipelines, methodological or conceptual contribution, evidence/experimental quality, relevance to Agent Memory, source credibility, recency, and whether it could change research direction or provide a useful new capability/benchmark. Check the primary paper/project/source yourself and verify that the claimed contribution is actually supported. Explicitly distinguish formally published work, arXiv-only work, and work still under review. Reject low-signal incremental updates, weakly supported claims, duplicate/redundant stories, and items that only match the keyword 'memory' superficially.

Selection priority is strict: (1) quality and deduplication; (2) recency; (3) completing all five slots. Before ranking, read `reported_items` and `paper_registry` from the supplied state; if the compact state is insufficient, read the full state file named in the operational context. Normalize each candidate to a canonical work identity across arXiv versions, DOI, ACL Anthology, OpenReview, project pages, repositories, title variants, and reposts. Exclude every item already present in `reported_items`, as well as semantic duplicates of a previously reported work. Do not reuse a previously reported item merely because the recent candidate pool is thin. A genuinely material new paper version, formal acceptance, benchmark result, dataset, or code release may be treated as an update only when the primary source supports the change; label it explicitly as an update rather than as a new paper.

Use chronological backfill instead of repetition. Start with the newest validated pool. If fewer than five high-quality unique items survive, move the publication cutoff backward in successive windows and continue primary-source verification until five items are available. Within the same quality tier, prefer the newer item, but never admit a weak, redundant, or superficially related item ahead of an older strong item. There is no fixed recency floor for backfill: continue backward through the verified literature as needed. The fallback changes freshness, not the quality threshold. Record an older item's true publication/event date and make the selection rationale clear that it is a historical high-value backfill, not a new release.

Then rank the validated candidates by importance and send exactly the Top 5 items that are genuinely worth occupying today's briefing slots. It is acceptable for an item without 'memory' in the title to rank highly if its mechanism materially advances Agent Memory. Roughly favor 70% direct Agent Memory and 30% adjacent research when the candidate quality supports that mix; do not force the ratio if the day's evidence does not justify it.

Every successful scheduled run is a daily briefing and must return `SUCCESS_NOTIFY` with exactly five unique cards. The absence of five newly published items is not a reason to return `SUCCESS_NO_NOTIFY`: use the chronological backfill process above. Use a date-scoped event key that includes the canonical identities, such as `agent-memory-frontier:YYYY-MM-DD:<five-canonical-ids>`. Use the strict `state_updates` operation array to preserve the existing registry and append all five canonical identities to `reported_items`, with their primary sources and accurate seen/notified metadata, so later runs can enforce cross-day deduplication. Each operation must contain an allowed `namespace`, `operation` set to `upsert`, and `value_json` containing one valid JSON value. Use `[]` when there are no updates. Use `FAILED` only for a genuine execution or evidence failure; do not silently skip a successful briefing.

For each of the final Top 5, include: rank; concise title; relevant image when available; publication/event date; status (published / arXiv preprint / under review / technical report / benchmark or code release); primary source; why it matters specifically for Agent Memory research; and a short selection rationale explaining why it survived the final filter. Order by significance first, using recency as a tie-breaker. Only include genuinely important items; quality over novelty-chasing.

The following requirements optimize only the Feishu card presentation. They do not replace or weaken the search, verification, filtering, or ranking workflow above. Design every final research card so that a reader can understand what the paper solves before opening the detail panel:

- Set `title` to the exact original-language paper title from the checked primary source, without shortening or editorial rewriting. Set `subtitle` to an accurate, natural Chinese translation of that title; do not use it for the date, status, or overview. For each paper, read the available full text (PDF or authoritative HTML body), not only the title or abstract, before writing the visible overview and detailed analysis. Avoid hype such as “breakthrough” or “groundbreaking” unless the primary evidence supports it.
- Set `focus.value` to `#1` through `#5` in rank order. Use visible fields labelled `日期`, `状态`, `Agent Memory 相关性`, and `入选理由`; keep the latter two concise and specific. The relevance must identify which memory stage or research capability is affected, rather than saying only that the work is important.
- Use exactly six ordered sections. Section 1 is `一句话概述` with `collapsed=false`. It must be exactly one natural Chinese sentence derived from reading the full text and state only (a) what problem the work solves and (b) how it solves it. Remove all experimental data, numbers, benchmark scores, comparisons, result claims, and evidence-boundary discussion from this visible sentence.
- Sections 2–6 are collapsed and must appear in this exact order: `论文摘要翻译`, `现存问题`, `已有方法的不足`, `当前方法为什么可行`, `未来展望`. `论文摘要翻译` must faithfully translate the complete abstract from the checked primary paper and must be the first item in the collapsed detail panel; do not replace it with an editor summary. The remaining four existing detail sections retain their current purpose and evidence requirements.
- `现存问题` states the actual research gap, failure mode, or capability bottleneck. `已有方法的不足` names the relevant comparison class and its specific limitation; if the source lacks a systematic comparison, say so instead of generalizing. `当前方法为什么可行` explains the chain from key mechanism, to the constraint or information flow it changes, to the supporting evidence. `未来展望` distinguishes author-stated future work from an editor inference based on stated limitations. If neither is supported, explicitly say that the source does not provide enough evidence for a safe projection.
- For a benchmark, dataset, code release, technical report, or official blog, keep the same six-section reading order but describe the correct object type. If the primary source does not contain a paper abstract, state that fact under `论文摘要翻译` and translate the source's own summary or overview without presenting it as a paper abstract. Do not present the object as a method paper or claim algorithmic superiority that the source does not establish.
